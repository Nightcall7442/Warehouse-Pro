## 🔴 КРИТИЧНО

### 1. Заказ с отрицательным количеством товара — накрутка склада любым агентом
**Файлы:** `api/order-router.ts:43-46`, `api/services/order.ts:225-234, 257-269`
Схема `order.create` не проверяет `quantity > 0` (в отличие от `arrival-router.ts:91`, где такая проверка есть). Проверка остатка `if (available < Number(item.quantity))` всегда проходит для отрицательного `quantity`, а потом сырой SQL `available = available - {quantity}` при отрицательном quantity **прибавляет** остаток. Доступно самой низкой роли (`fieldSalesQuery` — агент/мерчандайзер), не только оператору.
**Фикс:** добавить `.refine(v => Number(v) > 0, ...)` к `quantity` в схеме `order.create`, как уже сделано в `arrival-router.ts`.

### 2. Ещё 5 непочиненных мест с багом "пустая строка → decimal → 500"
Тот же класс бага, что чинили сегодня в product/arrival, подтверждён **двумя независимыми агентами** в:
- `api/agent-router.ts:104-119` (`saveLocation`, lat/lng) — **срабатывает на каждом GPS-пинге с телефона**, `.refine` не отсекает `""` (`Number("") === 0`, проходит диапазон -90..90).
- `api/agent-router.ts:425-460` (`createShop`, мобильное добавление точки), то же самое для gpsLat/gpsLng.
- `api/shop-router.ts:119-224` (`create`/`update` магазина, веб) — gpsLat/gpsLng вообще без `.refine`.
- `api/settings-router.ts:59-92` (`defaultReorderPoint`, `lowStockThreshold`) — при очистке поля в форме настроек.
**Фикс:** применить уже готовый `decimalOrDefault()` из `api/lib/zod-decimal.ts` (для lat/lng — свой вариант с диапазоном, т.к. там 0 — валидное значение, нужно отличать реальный 0 от пустой строки иначе).

### 3. 8 файлов миграций не зарегистрированы в `_journal.json`
**Файл:** `db/migrations/meta/_journal.json` (обрывается на `0021_add_block_unit`)
Файлы `0022_add_order_items_cost_price.sql` … `0029_fix_warehouse_stock_unique_index.sql` (и ещё нестандартный `001_photo_url_mediumtext.sql`) существуют на диске, но `drizzle-kit migrate` их не видит. Судя по всему, они были применены вручную (`drizzle-kit push`) на проде и никогда не попали в трекаемую историю миграций. Если сейчас развернуть БД с нуля через миграции — не будет: колонки `order_items.cost_price` (вставки в order_items сразу упадут), таблиц `visit_schedules`, `agent_territories`, колонок territories/sales_targets, исправленного уникального индекса на `warehouse_stock`, и **таблицы `onec_config` вообще нет ни в одной миграции** (интеграция с 1С не поднимется на чистом окружении).
**Фикс:** сгенерировать недостающие journal-записи (`drizzle-kit generate` со сверкой) или вручную дописать в `_journal.json`, затем проверить разворачивание на чистой тестовой БД.

### 4. Stripe-вебхук тихо ломает биллинг
**Файл:** `api/webhooks/stripe.ts:128-132`
Внутри транзакции вставка в `billingEvents` не указывает `tenantId` (колонка `NOT NULL`, `db/schema.ts:704-713`) — TS сам на это ругается (`TS2769`). Constraint-violation на этой строке **откатывает всю транзакцию**, включая активацию подписки (`checkout.session.completed`), отмену (`customer.subscription.deleted`) и флаг просроченного платежа (`invoice.payment_failed`). Stripe получает 500, ретраит — и падает так же снова и снова (идемпотентность по `stripeEventId` никогда не находит сохранённую запись, потому что она никогда не сохраняется). **В Stripe-дашборде всё выглядит успешным, а в базе — нет.**
**Фикс:** добавить `tenantId` во вставку (взять из уже определённого в обработчике контекста подписки/сессии).

### 5. "Бэкап" не создаёт бэкап
**Файл:** `api/cron/backup.ts:10-68`
Джоба только делает `SELECT COUNT(*)` по 8 таблицам и (если настроен S3) заливает JSON с этими счётчиками как "метаданные бэкапа" — сам код комментирует: *"Store backup metadata (actual dump would need mysqldump CLI)"*. Крон репортит `{success: true}` каждый раз. **Реального восстанавливаемого дампа не существует**, при этом мониторинг/крон выглядит здоровым.
**Фикс:** либо подключить реальный `mysqldump`/managed backup (Railway/PlanetScale snapshot), либо явно переименовать джобу и убрать ложное `success: true`, пока не будет настоящего бэкапа.

### 6. Мобильное приложение: скидка в заказе — денежный баг
**Файлы:** `src/components/order/OrderEditModal.tsx:38`, `src/components/order/OrderItems.tsx:~100`, `api/services/order.ts:620-626, 146, 206`
UI подписывает поле "Скидка (%)" и рисует "−15%", но бэкенд (`OrderService.update`/`.create`) трактует `discount` как **абсолютную сумму в сумах**: `newTotal = subtotal - discount`. Агент редактирует заказ на 500 000 сум, вводит "50000" ожидая скидку 50%, а по факту снимается 50 000 сум (10%). При этом мастер создания заказа (`app/order/new.tsx`) считает **построчную** скидку как настоящий процент — то есть в одном приложении два разных, несовместимых понятия "скидка".
**Фикс:** привести к одному контракту (проценты либо сумма) на всех трёх уровнях — мастер создания, экран редактирования, бэкенд — и явно промаркировать поле.

### 7. Мобильное приложение: скидка молча теряется при создании заказа
**Файлы:** `api/order-router.ts:43-46` (схема `items` принимает только `productId`/`quantity`, Zod молча отбрасывает лишние ключи), `app/order/new.tsx:556` (шлёт `unitPrice`/`discount` построчно — теряются), `src/api.ts:267-274` (top-level `discount` вообще не заполняется этим экраном)
Агент в 3-шаговом мастере применяет построчную скидку 10%, показывает владельцу магазина скидочный итог на экране — а бэкенд пересчитывает по полной цене без скидки. Для `paymentMethod: "debt"` это ещё и **долг магазина записывается без скидки**. Никакой ошибки не показывается — расхождение обнаруживается только постфактум.
**Фикс:** добавить top-level `discount` в отправку из `app/order/new.tsx`, либо реализовать построчные скидки на бэкенде, если бизнес-логика их предполагает.

### 8. Мобильное приложение: дубликат заказа при обрыве сети
**Файлы:** `app/order/new.tsx:552-559` (без `idempotencyKey`), `src/store/offline.ts:117-122` (ключ добавляется только в офлайн-очереди, уже ПОСЛЕ неудачной онлайн-попытки)
Если запрос дошёл до сервера и заказ создался, а ответ потерялся (таймаут 15 сек в `src/api.ts:25`) — клиент считает это сетевой ошибкой и ставит заказ в офлайн-очередь **с новым** idempotency-ключом. При следующей синхронизации создаётся **второй, дублирующий заказ** с повторным резервированием склада и повторной записью долга. Тот же пробел в `app/(tabs)/catalog.tsx:335-336,441` (там вообще нет ни ключа, ни офлайн-фолбэка).
**Фикс:** генерировать `idempotencyKey` **до** первой (онлайн) попытки и переиспользовать тот же ключ при повторе/офлайн-синке.

### 9. 4 непочиненных места с тем же React DOM-крашем ("insertBefore")
Тот же паттерн, который чинили в коммитах `57a53e2` (Products) и `390aaae` (Users): несколько соседних `{condition && <Modal/>}` без обёртки/key внутри одного flex-контейнера — реконсилятор React путает DOM-узлы при одновременном тогле двух и более модалок → белый экран.
- `src/pages/Shops.tsx:134,235,237,250,260,281` — 6 соседних условных блоков без ключей. **Высокая вероятность**, т.к. это ходовая страница.
- `src/pages/ShopDetail.tsx:174-175` — ровно та же форма из двух соседних условий, что крашила Products/Users.
- `src/pages/Warehouse.tsx:110-164` — `AdjustModal` и `createPortal(LowStock)` соседями, `AdjustModal` рендерится не в портал.
- `src/components/superadmin/TenantDetail.tsx:53-67` — почти дословно воспроизводит исходный баг из `952f062` (`<style>` внутри flex-контейнера) — эта правка сюда не докатилась.
**Фикс:** обернуть каждый conditional в свой `<div key="...">`, вынести `<style>` за пределы flex-контейнера — паттерн фикса уже есть в истории git (`57a53e2`, `390aaae`).

- **`api/api-key-router.ts:26-32`** — `list` без проверки роли (в отличие от `create`/`revoke`/`setStatus` в том же файле) — любой сотрудник может посмотреть список API-ключей тенанта.
