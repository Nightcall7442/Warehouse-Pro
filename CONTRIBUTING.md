# Работа с кодом

## Окружение

Нужен **Node ≥ 22.5** (в проекте используются возможности, которых нет в 20)
и **MySQL 8**.

```bash
npm install --legacy-peer-deps
cp .env.example .env
npm run db:migrate && npm run db:seed
npm run dev
```

## Что должно проходить перед отправкой

```bash
npm run check   # типы
npm run lint    # линтер
npm test        # проверки и покрытие
```

Все три обязаны завершиться кодом 0. Проверьте именно код возврата, а не
глазами по выводу: `npm test` печатает «N passed» и при этом падает по порогу
покрытия — такое уже случалось и приводило к «зелёному» отчёту о красной сборке.

## Записи в истории

Заголовок — по-русски, в повелительном наклонении, о том, **что меняется для
человека**, а не какие файлы затронуты:

```
Починить выбор категории и единицы в карточке товара
```

Тело — почему так, а не иначе: что было сломано, как это выглядело со стороны
пользователя, почему выбран этот способ. Через полгода важно именно это, а не
перечень строк — его покажет `git diff`.

## Комментарии в коде

Комментарий объясняет **причину**, а не пересказывает код.

Плохо:

```ts
// увеличиваем резерв на количество
reserved = reserved + qty;
```

Хорошо:

```ts
// Резерв ставится в той же транзакции, что и строки заказа: иначе между
// вставкой и обновлением остатка помещается второй заказ, и один товар
// уходит дважды.
```

Особенно это касается мест, где решение выглядит странным. Если код обходит
чужую особенность — напишите, какую именно, иначе следующий человек «починит»
обход обратно.

## Проверки

Новое поведение сопровождается проверкой. Проверка должна **падать без
исправления** — иначе она ничего не стережёт.

- Проверка отрисовывает настоящий компонент или страницу, а не их подобие.
  Копия логики в тесте проходит и тогда, когда рабочий код сломан.
- Денежные и складские правила проверяются **по числам**: остаток был X, стал
  Y. Ответ «сервер не упал» доказательством не является.
- Для проверок против настоящей базы есть `npm run test:db`, для сквозных —
  `npm run test:e2e`.

## Изменения схемы базы

Схема правится **только миграцией**. Ручные изменения в рабочей базе
рассинхронизируют её со снимком, и следующая сгенерированная миграция попробует
добавить то, что уже есть.

```bash
npm run db:generate   # сгенерировать по изменениям в db/schema.ts
```

Сгенерированный файл обязательно прочитайте. `drizzle-kit` сравнивает схему со
снимком, а не с рабочей базой: если снимок отставал, в миграцию попадут повторные
добавления существующих столбцов, и развёртывание упадёт.

Отдельная работа в CI применяет **всю цепочку миграций к пустой базе**. Если она
краснеет — новое окружение не поднимется с нуля, даже когда рабочее живёт
нормально.

## Границы ролей

Права проверяются не внутри обработчика, а выбором процедуры, на которой он
построен: `adminQuery`, `operatorQuery`, `fieldSalesQuery` и так далее (см.
`api/middleware.ts`). Новая ручка, построенная на `authedQuery`, открыта всем
вошедшим — это осознанное решение, а не умолчание.

## Чего делать не нужно

- Расширять область правки за пределы задачи. Заметили посторонний изъян —
  заведите задачу, а не чините попутно: смешанная правка нечитаема в истории.
- Отключать правило линтера точечным комментарием без объяснения причины.
- Оставлять `console.log`. Для журнала есть `api/lib/logger`.
- Класть секреты в код, в примеры или в проверки.
