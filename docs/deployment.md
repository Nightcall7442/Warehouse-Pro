# Развёртывание

## Что нужно

| Обязательно | Зачем |
|---|---|
| `DATABASE_URL` | Строка подключения к MySQL 8 |
| `APP_SECRET` | Подпись сессий. Возьмите случайные 48 байт: `openssl rand -base64 48` |

| Необязательно | Что включает |
|---|---|
| `APP_URL` | Публичный адрес приложения |
| `ALLOWED_ORIGINS` | Разрешённые источники запросов, через запятую |
| `REDIS_URL` | Общий кэш, общие пределы частоты, рассылка событий между экземплярами |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID` | Уведомления в Telegram |
| `STRIPE_*` | Подписки и оплата |
| `SMTP_*` | Почтовые уведомления |
| `CRON_SECRET` | Защита ручек, вызываемых по расписанию |
| `TRUSTED_PROXY_COUNT` | Сколько обратных прокси перед приложением — от этого зависит, какой адрес считается адресом клиента |
| `VITE_SENTRY_DSN`, `SENTRY_DSN` | Сбор ошибок |

Полный перечень — в `.env.example`. Секретов в репозитории нет.

## Railway

Сервис пересобирается и выкладывается сам при отправке в `main`.

- Сборка — по `Dockerfile` (см. `railway.json`).
- Проверка живости — `/health/ready`, срок ожидания 300 секунд.
- При падении — до 10 перезапусков.

## Docker

Перед первым запуском задайте в `.env` три значения, каждое — случайное:

```bash
openssl rand -base64 48   # APP_SECRET
openssl rand -base64 24   # MYSQL_PASSWORD
openssl rand -base64 24   # MYSQL_ROOT_PASSWORD
```

Готовых паролей в `docker-compose.yml` нет намеренно: без этих переменных
compose откажется стартовать и назовёт недостающую. Пароль приложения и пароль
`root` — разные; под `root` приложение не ходит.

```bash
docker compose up -d
```

Образ собирается многоступенчато, работает под непривилегированным
пользователем `appuser`, слушает порт 3000 и имеет собственную проверку живости.

**Что открыто наружу.** Только порт приложения. Порт базы привязан к
`127.0.0.1` и доступен лишь с самой машины — приложение ходит в неё по
внутренней сети compose, по имени `mysql`. Если подключаться к базе снаружи
контейнера не нужно, уберите у неё раздел `ports` целиком.

Приложение отвечает по http. В рабочей среде поставьте перед ним обратный
прокси с TLS и укажите настоящий адрес в `APP_URL` и `ALLOWED_ORIGINS` — иначе
ссылки в письмах и проверка источника запросов будут указывать на `localhost`.

## Миграции

Миграции применяются **внутри `dist/boot.js`**, а не в команде запуска.

Это сделано намеренно. Когда они стояли в команде запуска, платформа позволяла
переопределить её (`railway.json` это и делает) — и миграции молча переставали
выполняться. Именно так рабочая база однажды отстала от кода на несколько
миграций.

Поэтому: **не переносите миграции обратно в `startCommand`.**

Отдельная работа в CI применяет всю цепочку к пустой базе. Если она краснеет,
новое окружение не поднимется с нуля, даже когда рабочее живёт нормально.

## Проверка после выкладки

1. `/health/ready` отвечает успехом.
2. В журнале запуска есть строка о применённых миграциях.
3. Если задан `REDIS_URL` — в журнале должно быть **«Redis ready»**.
   Приложение поднимается и без Redis: при неудаче оно пишет
   «Redis unavailable, using in-memory fallback» и продолжает работать на памяти
   процесса. Отказ виден только в журнале, на экранах — нет, поэтому эту строку
   стоит проверять глазами после каждой правки переменных.
4. Вход настоящим пользователем и одно действие, меняющее данные.

## Наблюдение

Три слоя, и каждый отвечает на свой вопрос: показатели — «что-то не так»,
журнал — «почему», трассировка — «где именно».

### Показатели — Prometheus и Grafana

Приложение отдаёт метрики на `/metrics`. **В рабочей среде ручка закрыта, пока
не задан `PROMETHEUS_METRICS_TOKEN`** — иначе перечень маршрутов, объёмы
трафика, доли ошибок и состояние процесса были бы доступны всему интернету.

1. Задайте `PROMETHEUS_METRICS_TOKEN` — случайную строку.
2. В настройке сбора Prometheus укажите тот же ключ как `bearer_token`.
3. Импортируйте [docs/grafana/warehouse-pro.json](grafana/warehouse-pro.json):
   в Grafana `Dashboards → Import → Upload JSON`.

Готовые дашборды из сети (1860 «Node Exporter Full» и подобные) не подойдут:
они рассчитаны на `node_exporter`, которого здесь нет, и останутся пустыми.

### Журнал — Loki

`LOKI_URL` — адрес Loki, `LOKI_BASIC_AUTH` (вида `пользователь:пароль`), если
он закрыт. Записи уходят туда **вдобавок** к обычному выводу, поэтому журнал
Railway продолжает работать.

Отправка идёт пачками, в стороне от обработки запроса. Если Loki недоступен,
записи копятся до потолка в 2000 и дальше вытесняются самые старые: журнал
никогда не станет причиной отказа приложения.

В ярлыках Loki только три поля с малым числом значений — приложение, уровень,
среда. Идентификатор запроса, пользователь и маршрут лежат внутри строки JSON
и ищутся разбором на лету. Класть их в ярлыки нельзя: каждое сочетание ярлыков
у Loki — отдельный поток, и уникальный идентификатор запроса означал бы поток
на каждую запись.

Поиск по одному запросу целиком:

```
{app="warehouse-pro"} | json | correlationId="abc123def456"
```

### Трассировка — Jaeger

`OTEL_EXPORTER_OTLP_ENDPOINT` — адрес приёмника OTLP по HTTP, у Jaeger это
`http://<адрес>:4318/v1/traces`.

На запрос создаётся один промежуток: метод, шаблон маршрута, ответ,
длительность и `app.correlation_id` — по нему та же история находится в Loki.

Промежутков по обращениям к базе нет. Причина в комментарии
`api/lib/telemetry.ts`, коротко: автоматическая расстановка в OpenTelemetry
работает перехватом `require`, а сервер собирается в ESM — проверено, там она
не подменяет ничего. Расставлять их пришлось бы вручную по службам.

### Сквозная нить

У каждого запроса есть `correlationId`. Он же в заголовке ответа
`x-correlation-id`, он же в каждой строке журнала, он же атрибутом промежутка.
Взяв его из жалобы пользователя, вы находите и трассировку, и все записи.

Ошибки — в Sentry, если задан DSN.

## Резервные копии

`api/services/db-dump.ts` собирает копию сам — тем же соединением `mysql2`,
которым живёт приложение, — и передаёт её потоком, не складывая в память.
Согласованность даёт `START TRANSACTION WITH CONSISTENT SNAPSHOT`, то есть то
же, что `mysqldump --single-transaction`. Ночная копия в S3 (`api/cron/backup.ts`)
идёт этой же дорогой: двух способов снять копию быть не должно.

Внешнего `mysqldump` в образе нет намеренно. Он там стоял и не работал ни дня:
в Alpine пакет `mysql-client` — это клиент MariaDB, а он не умеет способ входа
`caching_sha2_password`, который MySQL 8 назначает пользователям по умолчанию.
Выгрузка падала с ошибкой 1045 на самом входе.

Если соединение не поднялось, снимок не начался или в базе нет ни одной
таблицы, операция падает — «успешной» пустая копия не считается. Обрыв уже
посреди передачи виден по тому, что архив не распаковывается: голый SQL в этом
случае выглядел бы целым текстом.

Восстановление:

```
gunzip -c warehouse-pro-<дата>.sql.gz | mysql -h <узел> -u <пользователь> -p <база>
```

Проверяйте копии восстановлением. Копия, которую ни разу не разворачивали, — не
копия.

### Снимки тома Railway — это другое

У тома MySQL включены снимки платформы: ежедневный (хранится 6 суток), недельный
(27) и месячный (89). Настраивать их не надо, они уже работают.

Они не заменяют логическую копию и наоборот:

| | Снимок тома | Копия из `db-dump.ts` |
|---|---|---|
| От смерти диска | да | да |
| Достать одну таблицу или заказ | нет, только вся база разом | да |
| Живёт вне Railway | нет | да, если задан S3 |
| Промежуток | до суток | по расписанию крона |

Восстановление снимка создаёт **новый** том с датой в имени и подключает его
вместо прежнего; прежний остаётся в проекте отсоединённым, и снимки, снятые
позже точки восстановления, не пропадают — они лежат на нём.

**Ночная копия не работает, пока не задан S3.** Без `S3_BUCKET`, `S3_ACCESS_KEY`
и `S3_SECRET_KEY` класть дамп некуда — файловая система контейнера не переживает
выкладку, — и крон честно возвращает отказ, а не ложный успех. Отдельный
`S3_BACKUP_BUCKET` нужен затем, чтобы копия не лежала в том же бакете, из
которого раздаются фотографии: его адрес знает любой пользователь.

## Хранилище файлов

Хранилище нужно двум вещам сразу: фотографиям товаров и ночной копии базы. Без
него фотография кладётся **прямо в MySQL** строкой `data:image/...` до 4 МБ —
база растёт от картинок, а каждый список товаров тащит их из неё же, — и ночная
копия отказывает: дампу некуда лечь.

### Что стоит сейчас

Своя служба **MinIO** в том же проекте Railway, том `minio-volume` на `/data`.
Карту привязывать не пришлось: платится там же, где остальное.

| | |
|---|---|
| Служба | `MinIO`, образ `minio/minio` |
| Команда запуска | `minio server /data --console-address :9001` |
| Адрес | `minio-production-9c62.up.railway.app`, порт 9000 |
| Бакет фотографий | `warehouse-pro-photos` — открыт на чтение |
| Бакет копий | `warehouse-pro-backups` — закрыт |

Ключи приложения — это ссылки Railway на переменные службы MinIO
(`${{MinIO.MINIO_ROOT_USER}}` и `${{MinIO.MINIO_ROOT_PASSWORD}}`), а не копии
значений: пароль меняется в одном месте.

### Бакеты заводятся скриптом

У MinIO в свежих сборках веб-консоли нет — создать бакет мышью негде:

```bash
railway run --service Warehouse-Pro -- node scripts/init-storage.mjs
```

Скрипт создаёт оба бакета, открывает на чтение **только** бакет фотографий и
отказывается работать, если имена совпали. Повторный запуск безопасен. Он же
отработает на любом другом S3-совместимом хранилище, если однажды переедем.

### Чего этот вариант не даёт

**Копии базы лежат на той же площадке, что и база.** Смысл копии — пережить
потерю площадки, и этого MinIO не даёт. От смерти диска по-прежнему берегут
снимки тома Railway (см. таблицу выше), но копия «вне Railway» — это отдельная
задача.

**Ключи приложения — корневые ключи MinIO.** Они могут всё, вплоть до удаления
бакетов. У обычного провайдера выдаётся ограниченный токен; здесь для этого
нужен отдельный пользователь MinIO, заводимый клиентом `mc`.

### Если переезжать на внешнее хранилище

| | Cloudflare R2 | Backblaze B2 | Amazon S3 |
|---|---|---|---|
| Бесплатно хранения | 10 ГБ | 10 ГБ | нет |
| Исходящий трафик | **бесплатно, весь** | бесплатно до 3× объёма хранения | платный весь |
| Карта при регистрации | нужна | нужна для публичного бакета | нужна |

Платит здесь не хранение, а **раздача**: фотографии тянут при каждом открытии
каталога. Переезд стоит смены четырёх переменных — `S3_ENDPOINT`,
`S3_PUBLIC_URL`, `S3_REGION`, `S3_FORCE_PATH` — плюс новых ключей; скрипт
заведения бакетов там отработает тот же.

### Ловушка с пробелом

Пароль, вписанный в панель с лишним пробелом на конце, MinIO при чтении своей
переменной обрежет, а клиент S3 — нет. Хранилище ответит
`SignatureDoesNotMatch`, при этом значения выглядят одинаковыми до последнего
символа. Приложение теперь снимает пробелы по краям со всех переменных при
чтении (`api/lib/env.ts`), так что повториться это не должно.
