# Развёртывание

## Что нужно

| Обязательно | Зачем |
|---|---|
| `DATABASE_URL` | Строка подключения к MySQL 8 |
| `APP_SECRET` | Подпись сессий. Возьмите случайные 48 байт: `openssl rand -base64 48` |

| Необязательно | Что включает |
|---|---|
| `APP_URL` | Публичный адрес приложения |
| `ALLOWED_ORIGINS` | Разрешённые источники запросов, через запятую |
| `REDIS_URL` | Общий кэш, общие пределы частоты, рассылка событий между экземплярами |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID` | Уведомления в Telegram |
| `STRIPE_*` | Подписки и оплата |
| `SMTP_*` | Почтовые уведомления |
| `CRON_SECRET` | Защита ручек, вызываемых по расписанию |
| `TRUSTED_PROXY_COUNT` | Сколько обратных прокси перед приложением — от этого зависит, какой адрес считается адресом клиента |
| `VITE_SENTRY_DSN`, `SENTRY_DSN` | Сбор ошибок |

Полный перечень — в `.env.example`. Секретов в репозитории нет.

## Railway

Сервис пересобирается и выкладывается сам при отправке в `main`.

- Сборка — по `Dockerfile` (см. `railway.json`).
- Проверка живости — `/health/ready`, срок ожидания 300 секунд.
- При падении — до 10 перезапусков.

## Docker

Перед первым запуском задайте в `.env` три значения, каждое — случайное:

```bash
openssl rand -base64 48   # APP_SECRET
openssl rand -base64 24   # MYSQL_PASSWORD
openssl rand -base64 24   # MYSQL_ROOT_PASSWORD
```

Готовых паролей в `docker-compose.yml` нет намеренно: без этих переменных
compose откажется стартовать и назовёт недостающую. Пароль приложения и пароль
`root` — разные; под `root` приложение не ходит.

```bash
docker compose up -d
```

Образ собирается многоступенчато, работает под непривилегированным
пользователем `appuser`, слушает порт 3000 и имеет собственную проверку живости.

**Что открыто наружу.** Только порт приложения. Порт базы привязан к
`127.0.0.1` и доступен лишь с самой машины — приложение ходит в неё по
внутренней сети compose, по имени `mysql`. Если подключаться к базе снаружи
контейнера не нужно, уберите у неё раздел `ports` целиком.

Приложение отвечает по http. В рабочей среде поставьте перед ним обратный
прокси с TLS и укажите настоящий адрес в `APP_URL` и `ALLOWED_ORIGINS` — иначе
ссылки в письмах и проверка источника запросов будут указывать на `localhost`.

## Миграции

Миграции применяются **внутри `dist/boot.js`**, а не в команде запуска.

Это сделано намеренно. Когда они стояли в команде запуска, платформа позволяла
переопределить её (`railway.json` это и делает) — и миграции молча переставали
выполняться. Именно так рабочая база однажды отстала от кода на несколько
миграций.

Поэтому: **не переносите миграции обратно в `startCommand`.**

Отдельная работа в CI применяет всю цепочку к пустой базе. Если она краснеет,
новое окружение не поднимется с нуля, даже когда рабочее живёт нормально.

## Проверка после выкладки

1. `/health/ready` отвечает успехом.
2. В журнале запуска есть строка о применённых миграциях.
3. Если задан `REDIS_URL` — в журнале должно быть **«Redis ready»**.
   Приложение поднимается и без Redis: при неудаче оно пишет
   «Redis unavailable, using in-memory fallback» и продолжает работать на памяти
   процесса. Отказ виден только в журнале, на экранах — нет, поэтому эту строку
   стоит проверять глазами после каждой правки переменных.
4. Вход настоящим пользователем и одно действие, меняющее данные.

## Наблюдение

- Prometheus снимает показатели, Grafana их показывает.
- У каждого запроса есть идентификатор (`correlationId`) — по нему записи в
  журнале сшиваются в одну историю.
- Ошибки — в Sentry, если задан DSN.

## Резервные копии

`api/services/db-dump.ts` вызывает настоящий `mysqldump` и передаёт вывод
потоком, не собирая его в памяти. Если `mysqldump` не запустился, завершился с
ошибкой или не выдал ни одной строки, операция падает — «успешной» пустая копия
не считается.

Проверяйте копии восстановлением. Копия, которую ни разу не разворачивали, — не
копия.
