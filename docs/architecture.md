# Архитектура

Документ отвечает на вопросы, ответы на которые иначе приходится выкапывать из
кода: как компании отделены друг от друга, кто считает деньги и почему остаток
на складе — это три разных числа.

---

## Один процесс

Сервер, интерфейс и статика собираются в один процесс Node. Vite собирает
клиент, esbuild — сервер; на выходе `dist/boot.js`, который раздаёт и то, и
другое.

Отдельного сервера приложений нет намеренно: при нынешнем размере он добавил бы
ещё одну точку отказа и ещё один шаг развёртывания, не дав ничего взамен.

```
Браузер ─┐
         ├─→ Hono ─→ tRPC ─→ службы ─→ Drizzle ─→ MySQL 8
Телефон ─┘
```

## Изоляция компаний

В каждой таблице с данными клиентов есть столбец `tenant_id`.

Ключевое решение: **фильтр по компании ставится не в запросе, а до него.**
Промежуточный слой `withTenantIsolation` кладёт компанию в контекст, и до
бизнес-логики запрос доходит уже с ней. Разработчик не может забыть условие в
отдельно взятом месте, потому что это условие пишется не там.

Порядок слоёв (см. `api/middleware.ts`):

```
withCorrelationId    идентификатор запроса — сшивает записи в журнале
withTenantIsolation  компания из сессии кладётся в контекст
withGlobalRateLimit  общий предел частоты
requireAuth          сессия обязательна
withSubscriptionGate подписка компании действует
requireRole([...])   роль допущена к этой ручке
mutationRateLimit    отдельный предел для действий этой роли
```

Права даёт не проверка внутри обработчика, а выбор процедуры, на которой он
построен:

| Процедура | Кому доступна |
|---|---|
| `publicQuery` | Всем, без входа |
| `authedQuery` | Любому вошедшему |
| `adminQuery` | `ceo` |
| `operatorQuery` | `ceo`, `operator` |
| `fieldSalesQuery` | `ceo`, `operator`, `agent`, `supervisor`, `merchandiser` |
| `supervisorQuery` | `ceo`, `supervisor` |
| `courierQuery` | `ceo`, `operator`, `courier` |
| `superAdminQuery` | `superadmin` (управление платформой) |

Ручка, построенная на `authedQuery`, открыта всем вошедшим. Это должно быть
осознанным решением.

## Склад: три числа, а не одно

Наивный учёт хранит один остаток, и на нём один товар продаётся дважды: между
проверкой «хватает ли» и списанием помещается второй заказ.

Здесь остаток разложен на три величины:

| Величина | Что означает |
|---|---|
| `currentStock` | Физически лежит на складе |
| `reserved` | Обещано по оформленным, но не отгруженным заказам |
| `available` | `currentStock − reserved` — что можно обещать ещё |

**Создание заказа** увеличивает `reserved` и уменьшает `available`;
`currentStock` не меняется — товар ещё на складе.
**Отгрузка** уменьшает `currentStock` и `reserved`.
**Отмена** возвращает `reserved` и `available`.

Резерв ставится **в той же транзакции**, что и строки заказа, одним запросом
`UPDATE ... CASE WHEN`. Отдельным запросом после вставки между ними успевал
поместиться другой заказ.

Об этом же — ограничение `uq_order_items_order_product`: один товар может
встречаться в заказе только один раз. MySQL берёт первое совпавшее `WHEN`, и
вторая строка с тем же товаром молча не резервировалась — в заказе 120 единиц,
на складе занято 60. Запрет стоит в базе, а не в одной проверке, чтобы
действовать на все пути сразу: создание, правку, отмену, удаление,
восстановление.

Каждое изменение остатка попадает в журнал движений с причиной и автором.

## Деньги

**Считает сервер.** Приложение показывает свою сумму, но к оплате идёт та, что
посчитал сервер по своим ценам на момент отправки. Цены в приложении могут
устареть, пока агент ходит по маршруту.

**Скидка — процент.** На входе проверяется рамкой от 0 до 100, затем переводится
в деньги и хранится суммой: отчёты о выручке складывают этот столбец, и он
должен означать «сколько денег скидано», а не «сколько процентов».

Скидки по отдельным строкам, которые агент ставит в приложении, сворачиваются в
один равносильный общий процент — так к оплате выходит ровно та сумма, которую
агент назвал владельцу магазина.

**Долг магазина не ведётся руками, а выводится.** Он пересчитывается из заказов,
платежей и возвратов (`api/services/shop-debt.ts`). Ручное «прибавить сюда,
отнять отсюда» расходится с действительностью при первой же отмене заказа
задним числом.

## Работа без связи

Агент в подвале магазина должен оформить заказ. Приложение кладёт его в
локальную очередь и отправляет, когда связь вернётся.

Опасность здесь — дубли: отправка ушла, ответ не дошёл, приложение пробует
снова. Поэтому у каждого заказа есть **ключ идемпотентности**: сервер, увидев
знакомый ключ, возвращает уже созданный заказ, а не делает второй.

После отправки приложение сверяет сумму, которую агент назвал владельцу, с той,
что вернул сервер, и предупреждает о расхождении. Молча менять сумму нельзя —
её уже произнесли вслух.

## Обмен с 1С

Через OData. Товары и контрагенты приходят из 1С, реализации уходят обратно.
Соответствие идентификаторов хранится в `id_mappings`, состояние обменов — в
`sync_status`.

Сущности при обмене не удаляются, а помечаются недействующими: удаление на одной
стороне не должно уносить историю на другой.

---

## Живое обновление

Server-Sent Events вместо опроса по таймеру. Экран руководителя обновляется, когда
событие произошло, а не через 30 секунд после.

## Что где лежит

| Каталог | Что внутри |
|---|---|
| `api/*-router.ts` | Ручки: разбор входных данных, права, вызов службы |
| `api/services/` | Бизнес-логика. Здесь считаются деньги и остатки |
| `api/lib/` | Общее: журнал, кэш, окружение, разбор чисел |
| `api/middleware.ts` | Компания, вход, роли, пределы частоты |
| `db/schema.ts` | 45 таблиц |
| `db/migrations/` | 46 миграций; правится только через них |
| `src/pages/` | 42 страницы веб-интерфейса |
| `contracts/` | Типы, общие для сервера и клиента |

Правило разделения: роутер отвечает за «кому можно и что пришло», служба — за
«что это значит». Расчёт денег в роутере рано или поздно разойдётся со вторым
роутером, который считает то же самое.
