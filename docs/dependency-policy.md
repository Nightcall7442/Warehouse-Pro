# Как обновляем зависимости

Сверено по `package.json` и `npm outdated` на 29.09.2026.

## Порядок

| Что | Когда | Как |
|---|---|---|
| Исправления безопасности | Сразу, как только `npm audit` показал high или critical | Отдельным PR, только нужный пакет |
| Патчи и миноры | Раз в месяц | Одним PR «зависимости за месяц» |
| Мажоры | По одному, отдельной задачей | Своим PR, со своим разбором (см. ниже) |

Ежемесячный PR делается так:

```bash
npm audit                                # записать «до»
npm update --legacy-peer-deps            # в пределах диапазонов package.json
npm audit fix --legacy-peer-deps         # без --force: --force поднимает мажоры
npm audit                                # записать «после»
```

И проверяется тем же, чем выкладка:

- Чистая установка в отдельной копии, как в Dockerfile: скопировать
  `package.json` и `package-lock.json` во временный каталог и выполнить там
  `npm ci --legacy-peer-deps --dry-run`. Строгий `npm ci` падает при
  расхождении двух файлов — лучше узнать об этом здесь, чем на выкладке.
- `npm run check`, `npm run lint`, весь `npm test`, `npm run test:db`,
  `npm run build`.

Правила, выученные на опыте:

- **`package-lock.json` — только через npm.** Когда он расходится с
  `package.json`, строгий `npm ci` в образе падает, а `npm install` у
  разработчика проходит. Так однажды сломалась выкладка с prom-client.
- **`--legacy-peer-deps` — в каждой команде npm**, и в установке, и в
  обновлении. Файл блокировки собран с ним, и без флага `npm ci` считает его
  рассинхронизированным (после 29.09 — из-за `ajv`, которого
  `@apideck/better-ajv-errors` просит как peer). Первоначальная причина —
  `vite-plugin-pwa` не принимал Vite 7 — ушла: 1.3 его принимает, и без флага
  зависимости разрешаются без конфликтов. Снять флаг можно отдельной правкой:
  пересобрать блокировку без него и убрать его из Dockerfile и CI разом.
- **zod.** Миноры могут менять тексты ошибок проверки, а их видит человек на
  экране. Проверки, сверяющие текст, краснеют — это не всегда поломка кода,
  но разбирать каждую. 29.09: 4.4.3 → 4.6.5, весь набор зелёный.
- **Пакеты 0.x (OpenTelemetry, esbuild).** Для них минор — это мажор:
  `^0.220.0` не пускает дальше 0.220.x, поэтому `npm update` их не двигает.
  OpenTelemetry поднимается руками, все `@opentelemetry/*` 0.x разом (они
  выпускаются согласованно), и после — `telemetry-exports-spans.test.ts`.
- **Пакет в `dependencies` уходит в боевой образ** со всеми своими
  зависимостями. Неиспользуемый — удалить, нужный только при сборке — в
  `devDependencies`. Стережёт `every-dependency-is-imported.test.ts`.

## Node

Один мажор везде: `FROM node:…` в Dockerfile, `node-version` в каждом
задании `.github/workflows`, `engines` в `package.json`, мажор `@types/node`.
Расхождение ловит `api/__tests__/node-version-is-one.test.ts`.

С 29.09.2026 это Node 24 (поддержка до 30.04.2028; у 22 — до 30.04.2027).

**Что изменилось для обмена с 1С.** Мост ходит к серверу клиента обычным
`fetch` (`api/lib/safe-fetch.ts`), своих настроек TLS нет — действуют
умолчания Node. Node 24 (OpenSSL 3.5.7) проверен на местном учебном сервере:
он отказывает серверу с ключом RSA-1024 («EE certificate key too weak») и с
сертификатом, подписанным SHA-1 («CA signature digest algorithm too weak»);
обычный сертификат (RSA-2048, SHA-256) проходит. Настоящий сервер 1С для
проверки недоступен. Публикации 1С по `http://` это не касается. Если у
клиента после выкладки «проверка связи» с 1С по `https://` перестанет
проходить — причина, скорее всего, в его сертификате: лечится новым
сертификатом на его стороне. Ослаблять проверку у себя (`--tls-cipher-list`
с `SECLEVEL`) — только временно и на всё приложение сразу.

## MySQL

Бой — 9.4, и все задания с базой гоняются на ней. 9.4 исправлений
безопасности больше не получает; путь — 9.7 LTS обновлением на месте.
Проверки с настоящей базой (`real-db` в `ci.yml`) уже идут на обеих версиях;
задание на 9.7 называется «real-db (MySQL 9.7)» и в обязательные проверки
ветки пока не входит. Упав, оно остаётся красным в списке проверок, но не
держит ни слияние, ни выкладку: у него `continue-on-error`. Это важно из-за
«Wait for CI» у службы в Railway — он смотрит на итог всего потока CI, и без
`continue-on-error` красная 9.7 пропускала бы каждую выкладку боя на 9.4.
Если решено, что 9.7 должна держать и выкладку, — `optional: true` у её
ветви в `ci.yml` заменить на `false` (и поправить проверку
`ci-mysql-matches-production.test.ts`).

Порядок переезда: несколько недель зелёного «real-db (MySQL 9.7)» → копия
базы → обновление боя в окно → `PRODUCTION_MYSQL` в
`api/__tests__/ci-mysql-matches-production.test.ts` и образы во всех потоках
и в `docker-compose.yml` — на 9.7. Обновление однонаправленное: база,
открытая 9.7, в 9.4 уже не откроется, поэтому копия — до, а не после.

## Dependabot

Не включён — это решение владельца. Что даст включение
(`.github/dependabot.yml`):

- PR на обновления по расписанию — для npm и для действий GitHub; патчи и
  миноры можно собирать в один PR (`groups`), как в месячном порядке выше.
- Отдельные PR на исправления безопасности сразу после публикации
  уязвимости (включается в настройках репозитория, Security → Dependabot).
- Мажоры из списка выше выключаются правилами `ignore` с
  `update-types: ["version-update:semver-major"]` — иначе на каждый будет
  висеть PR.
- Каждый PR проходит те же обязательные проверки (`check`, `e2e`,
  `real-db`); сливает по-прежнему владелец.
- Флаги npm Dependabot берёт из `.npmrc`, а его в репозитории нет:
  `--legacy-peer-deps` передаётся в каждой команде. Без `.npmrc` с
  `legacy-peer-deps=true` (или без снятия флага, см. выше) его PR могут
  собрать блокировку не так, как наши команды, — это видно по первым же PR.
