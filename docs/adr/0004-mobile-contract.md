# 0004. Контракт мобилки проверяется типами в CI обоих репозиториев

Дата: 2026-09-12. Код: `scripts/mobile-contract.mjs`, `api/contract.ts`,
`contracts/mobile-procedures.json`, джобы `mobile-contract` (веб) и `contract` (мобилка).

## Контекст

Мобильное приложение — отдельный репозиторий: axios строками (`"order.getById"`)
и 54 рукописных интерфейса. Переименование поля на сервере проходило CI веба
и ломало APK у агентов; узнавали от них. Первая же проверка нашла: оценка KPI
не показывалась никогда (`grade` против `kpiGrade`), средний процент плана был
NaN (`completion` против `revenueCompletion`), два статуса заказа существовали
только в мобилке, строки заказа считались числами при строках с сервера.

## Решение

Скрипт читает `src/api.ts` мобилки (AST), берёт типы и подписи функций текстом —
без импортов, чтобы react-native не попал в серверную программу, — и для
каждого вызова генерирует проверку: ответ (`inferRouterOutputs`, Date → string)
присваиваем типу мобилки; вход из параметров функции присваиваем
`inferRouterInputs`; путь существует. Поблажка одна: необязательное поле мобилки
принимает null сервера. Проверка идёт в CI веба (выкачивает мобилку) и в CI
мобилки (выкачивает веб); список путей и рода (query/mutation) сверяется vitest
без второго репозитория.

Рассматривали общий npm-пакет типов: два репозитория, два релизных цикла и
пересборка APK на каждую правку типа — дороже, чем проверка.

## Последствия

Правка контракта видна в обоих CI до сборки APK. Мобилка держит ветку, из
которой собирается APK, в `master` (или задаёт `MOBILE_REF`).
