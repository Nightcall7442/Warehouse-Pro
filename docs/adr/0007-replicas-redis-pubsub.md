# 0007. Вторая реплика: Redis pub/sub с меткой процесса

Дата: 2026-09-12. Код: `api/lib/redis.ts` (`subscribeChannel`, `INSTANCE_ID`),
`lib/sse.ts`, `lib/cache.ts`, тест `two-replicas-share-sse-and-cache`.

## Контекст

Живые обновления (SSE) и кэш жили в памяти одного процесса. Код для Redis был,
но мёртвый: шина подписывалась в конструкторе до подъёма Redis, подписка не
ставилась никогда; заработай она — процесс получал бы своё событие обратно и
раздавал его дважды. Кэш писал в Redis, но читал только память: сброс на одной
реплике не трогал память другой до конца TTL.

## Решение

Подписка ленивая — при первом событии после подъёма Redis; одна на процесс,
обработчиков сколько угодно. Каждое сообщение несёт `INSTANCE_ID` отправителя,
свои отбрасываются. SSE: чужие события идут слушателям и в историю догона.
Кэш: сброс (ключ / префикс / всё) рассылается по `cache:invalidate`; `withCache`
при промахе в памяти читает Redis и кладёт в память не дольше остатка срока —
иначе две реплики продлевали бы значение друг другу бесконечно. Без Redis всё
как было.

Остальное для второй реплики уже было готово: сессии — JWT с отзывом в Redis,
лимиты — Redis, планировщик — `GET_LOCK` в MySQL, файлы — S3.

## Последствия

Вторую реплику можно включать при заданном `REDIS_URL`. Синхронное `cache.get`
на другой реплике даёт промах, не устаревшее значение.
