# 0001. Остаток меняется только через дверь

Дата: 2026-09-12. Код: `api/services/stock-ledger.ts`, страж `stock-door-is-the-only-writer`.

## Контекст

Остаток на складе (`warehouse_stock`) писали девятнадцать мест: заказ, отгрузка,
корректировка, перемещение, приход, возврат, импорт, вебхук 1С — каждое своим
UPDATE и своей арифметикой. Резерв уходил в минус, `available` расходился с
`current − reserved`, партии (FEFO) было не на что опереть: никто не знал, какая
из девятнадцати дорог сработала.

## Решение

Одна служба — `receiveStock / reserveStock / releaseStock / shipStock /
applyStockEffect / setStock` — единственный писатель. `available` не хранится, а
выводится (`current − reserved`). Сырой `UPDATE warehouse_stock` вне двери
запрещён стражем; потолок — две строки, обе внутри самой двери. Партии
списываются FEFO внутри двери; просроченные партии отгрузка не берёт, списание
берёт первыми.

Рассматривали: триггеры в MySQL (невидимы из кода, не тестируются без базы) и
«дисциплину» (уже не сработала девятнадцать раз).

## Последствия

Любая новая операция со складом — через дверь, иначе тест красный. Тесты с
подделкой базы обязаны знать её SQL (`helpers/mock-execute`). Цена — все
изменения остатка идут через один файл; это и есть цель.
